# 移行プラン（現行LLM → 新系統）

現行の Logic Horse（①〜⑤のプロンプト連鎖）は **実戦・X・RPM-10 のまま残す**。  
新系統 `next/` は **同じ開催をペーパーで回し、勝ってから主軸を移す**。

---

## ゴール

- 印の決定を「AIの文章判断」から「DB数値の勝ちきり照合」に移す
- オッズは最終印に使わず、ケン（床/EV）だけに使う
- 的中率と回収率が同時に悪い状態を、見送り込みで改善できるか検証する

---

## フェーズ

### P0 止血（現行を使い続ける週）

現行コードは変えない。プロンプト運用だけ短くする。

1. ⑤で最新オッズを渡して印を変えさせない（表示のみ）
2. プロンプトを増やさない（固定1本）
3. 混戦・情報不足は見送り

目的: 悪化の主因（人気追随・プロンプト肥大）を止めて、比較の土台を安定させる。

### P1 同じレースを2本出す

入力は同じ JRA公式 DB。

```text
jv_data.db
  ├─ 現行: ①抽出 → ②〜⑤ LLM予想（いまのまま）
  └─ next: predict --db --date
       勝ちきり照合 → 印 → T1〜T7 → オッズ床
```

比較表（1レース1行）:

| 項目 | 現行 | next |
| --- | --- | --- |
| 買う/ケン | | |
| ◎馬番 | | |
| 券種 | | |
| 的中 | | |
| 払戻 | | |

RPM-10 は現行側の公開指標のまま。next は内部KPI（的中・回収・見送り率）。

### P2 勝ちきりスコアを実データで調整

`next/` の `win_score` は骨格のみ。実DBで次を確認する。

1. `inspect` でテーブル名が検出できるか
2. 過去走が当該日前だけか（リークなし）
3. ◎が「複勝は強いが勝ちきれない馬」になっていないか
4. 神戸新聞杯型（軸堅・下位荒れ）が Chaos で全部ケンになっていないか

重みはバックテストの的中・回収を見てから変える。プロンプトは増やさない。

### P3 置き換え判定

次を満たすまで実戦主軸は現行。

- 同一期間・見送り込みで next の回収が現行以上
- Pass の的中が極端に落ちていない
- 目安: Pass 50レース以上（理想は数開催）
- 一発高配当だけで勝っている場合は不採用

満たしたら、Xと実戦の主軸を next に移す。RPM-10 の定義は別判断（継続可）。

---

## やらないこと

- 現行の①〜⑤を新系統の中に残して「AIが最終印」にすること
- 最新オッズを印の特徴量に入れること
- 現行コード（Logic Horse）の改変
- 合成オッズの先回り実装

---

## 直近の作業順

1. `jv_data.db` のパスで `inspect`  
2. 直近1開催を `predict`  
3. 現行の◎と next の◎を表にする  
4. ズレたレースだけ勝ちきり条件を見直す  
5. 数開催分のペーパー比較 → P3 判定
